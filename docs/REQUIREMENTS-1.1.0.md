# 5. 两层状态及修改规则

分别管理：

A. 流程状态：
Discussion → candidate → reviewed → frozen → bootstrapped → validated → accepted。

B. 决策项状态：
能够表达未确定、已提议、已确认、需复核，以及不适用和本轮不做等语义。

具体 enum 命名由实现确定，但必须满足以下规则：

1. Agent 建议不等于用户确认。
2. 用户明确确认、用户授权的默认值、既有规范继承和 Agent 建议必须可区分、可追溯。
3. 不得仅凭 Agent 自填 confirmed=true 就宣称有真实用户授权；记录可核对的来源依据。
4. “不适用”“本轮不做”“拒绝某个候选方案”不能混用。
5. 拒绝一个候选不代表整个问题已经解决。
6. 必要假设必须标明性质；影响实质性架构决定的未确认假设不得暗中变成正式结论。
7. 冻结后的变更从对应版本开启新的变更讨论，不能直接原地重写历史架构。

用户明确修改某项决定时：

- 按用户要求更新该项；
- 基于依赖关系识别受影响的下游；
- 下游保留旧值以供比较，但标记需复核；
- 已失效值不得继续参与正式生成；
- 无关节点保持原状态，不能清空整轮讨论；
- 使受影响的候选和审查失效，不能复用旧 PASS；
- 给出简洁的修改结果和影响范围。

如果用户要求相互冲突，记录冲突并阻塞受影响的正式流程，不自行选择忽略某一项。

# 6. 调度规则与检查队列

优先级数字越小，主动补问优先级越高。

优先级控制“下一步主动补问什么”，依赖关系控制“结论是否有效”，不是强制用户按固定问卷回答。

用户提前提供的信息随时接收；已经明确回答的内容不得重复询问。同优先级按依赖和稳定顺序调度。

某项暂时受阻时，可以推进不依赖它的其他事项，但不能绕过最终门禁。验证依赖引用与循环，不能让错误依赖导致静默跳过或无限循环。

采用以下检查组：

## 优先级 0：目标与范围

确认：

- 实现什么系统；
- 目标用户与关键业务场景；
- 本轮目标、边界和非目标；
- 可判断完成与否的验收标准；
- 影响选型的硬约束，例如平台、规模、安全或运行环境要求。

架构讨论保持合适粒度，不把所有实现细节都升级成人工决策。

## 优先级 0：预算与可行性

确认目标期限，并至少明确一种资源约束：

- 人力；
- Agent 订阅或能力资源；
- 资金。

记录须足以支持判断：

- 人力：人数、可投入时间或工作量；
- Agent：产品或能力类型、数量、可用约束；
- 资金：金额、币种、周期和覆盖范围。

区分用户约束与 Agent 估算。估算记录依据、假设和不确定性，不把估算冒充承诺。

未填写不等于零，没有明确上限不等于无限。

范围或关键方案变化后重新检查预算可行性。冲突时提出缩减范围、修改方案或调整预算的选项，不自行扩大预算或删除需求。

## 优先级 1：仓库与交付基线

Greenfield 默认沿用 1.0.0：

- Git；
- GitHub repository 与 PR 流程；
- 本地验证和 GitHub CI 共用 Validation Contract；
- main、task branch/worktree；
- 既有审查、保护规则和集成写回要求。

用户明确要求其他方式时记录差异。

Existing Repository 优先继承既有规范、包管理器、版本约定与 DevOps，不用默认值覆盖现状。

区分“选择某方案”“获得操作授权”“配置完成”“真实运行通过”。

GitHub CI/CD 不自动代表已授权生产部署；本地 CI 不自动代表需要本地部署。发布和部署边界按实际需求确认。

## 优先级 2：系统组成与技术栈

允许同时激活多个分支，至少识别一类实际组件：

A. 服务器；
B. 通用应用客户端；
C. 游戏客户端；
D. Web；
E. 其他，例如 CLI、SDK、库、批处理工具。

使用一份总状态和按需激活的分支，共享跨组件决定，避免多份互相矛盾的答案。

服务器按需确认：

- 部署与协作形态；
- 语言与框架；
- 持久化需求及数据库；
- 中间件及其必要职责。

消除“是否分布式”的歧义，按实际需求区分单实例、同一服务多副本、多个协作服务等情况。

通用客户端按需确认 Desktop、Mobile、目标平台、语言和框架。

游戏客户端按需确认 Desktop、Mobile、目标平台、引擎和语言。

Web 按实际需要确认目标运行环境与技术方案。

允许没有数据库、没有中间件、没有框架。不得因为检查项存在就引入对应组件。

API 契约不再作为与服务器、客户端并列的产品形态。它属于跨组件边界检查；API-only 服务可归入服务器或其他实际服务组件。

## 优先级 3：契约与业务数据流

围绕关键业务场景描述：

- 发起方、参与组件和职责；
- 请求、响应、事件或推送路径；
- 通信契约和数据归属；
- 状态变化、成功依据和失败行为；
- 按需展开鉴权、授权、事务、顺序、幂等、超时、重试和一致性。

不得固定生成 gateway → db → client 链路。

Gateway、缓存、数据库、队列等只在已确认方案需要时出现。没有某组件就不补造该组件。

根据实际适用性覆盖异步任务、服务器推送、离线同步等路径，不要求所有项目实现它们。

## 优先级 3：GUI 与交互

GUI 与数据流分开，仅对适用项目激活。

确认：

- 风格；
- 页面与布局；
- 导航方式；
- 关键交互状态；
- 页面或用户操作与业务能力、契约或本地能力的映射。

区分本轮真实功能、纯展示页面、占位功能和后续规划。

不得因为出现一个页面或按钮就擅自新增后端功能或 API。

## 优先级 4：完整性复核

复用并扩展既有 concerns 定义，避免在 Skill、状态机和冻结代码中维护互相漂移的三套清单。

覆盖适用的安全、认证授权、配置与密钥、持久化、事务、缓存、异步消息、顺序、一致性、幂等、可观测性、故障处理、部署、回滚、兼容、迁移、测试、CI/CD、发布与运维。

每项有明确适用性和依据；检查某关注点不等于必须实现某能力。

影响技术选择的硬约束应提前讨论，不能以优先级 4 为理由拖到最后。

## 优先级 4：正式流程准入

检查：

- 本轮必需决定闭合；
- 没有需复核的有效输入；
- 没有阻塞冲突；
- 排除和不适用项有依据；
- 范围、验收和预算一致；
- 候选和当前状态绑定。

通过只表示具备进入正式流程的条件，不等于已获冻结授权。

# 7. 状态展示、并发与跨 Agent 续接

支持用户自然语言查询：

- 当前已经确认的内容；
- 全部讨论状态；
- 未确定和需复核事项；
- 某次修改的影响；
- 下一步需要讨论什么。

在对话中展示简洁表格，至少能够包含稳定 ID、优先级、状态、结论和待处理事项。

表格从实际状态生成，不另存一份手工维护的答案表。用户查询确认内容时，不能把 Agent 建议混入已确认结果。

read/status/show 等查询是只读操作，不能顺便修改 revision、确认默认值、推进阶段或冻结。

采用单写入者：

- 协调 Agent 提交状态；
- 其他 Agent 提交提议或审查结果；
- 每次修改校验 expectedRevision；
- revision 校验和状态写入必须作为受保护的整体执行，避免两个并发写入都通过检查；
- 使用原子写入及必要的最小锁机制；
- 中断、陈旧 revision、锁冲突和损坏状态有明确可恢复处理；
- 不静默覆盖、不静默重置空状态。

多个 worktree 中必须明确当前 discussion 的权威工作副本和基线。其他副本不能各自成为新的权威状态。集成时检查状态版本与冲突。

新上下文应能依据 canonical 规范、进度入口和被明确指向的工作状态继续，不依赖前一 Agent 的私有记忆。

# 8. 最终快照与归档生命周期

默认最终归档位置：

spec/architecture/discussions/<discussion-id>/STATE.json

已有项目继承获批的布局。

每轮讨论只保留一份最终讨论快照，不保留每一轮完整状态副本和无价值的中间草稿。

但是必须保留：

- 有效决定的确认依据；
- 必要约束和假设；
- 重要排除理由；
- 与候选、审查、冻结的关联；
- 既有治理要求保留的独立审查证据和真实宿主轨迹。

“只保留最终结果”不意味着删除 Git 历史、正式架构历史、原始审查证据或必要的迁移恢复资料。

Greenfield 在仓库初始化和必要规范入口建立完成后，完成最终归档和恢复入口衔接。不得把单独 git init 成功当作归档条件已经全部满足。

Existing Repository 在相应获批变更流程完成后归档，不等待不存在的首次初始化。

归档必须：

1. 校验目标路径及授权；
2. 写入完整快照；
3. 验证内容、哈希和关联；
4. 更新可恢复入口；
5. 再清理不再需要的中间草稿。

归档失败保留当前工作状态；清理失败记录待处理，不伪造全部完成。

重复归档应幂等；同一 discussion ID 出现不同最终内容时报告冲突，不覆盖历史快照。

归档后保留 WORKING.json，记录本轮终态及归档引用。新一轮讨论使用新的 discussion ID，并记录基线来源；旧快照不再原地修改。

独立审查必须能获得不可变的原始输入快照。即使最终归档发生在后续阶段，审查也不能依赖未来会改变的 WORKING.json。

设计清晰的内容绑定，避免：

- 流程状态推进本身改写已审查输入；
- 更新归档位置后破坏已有有效证据；
- snapshot 与 manifest 之间形成循环哈希；
- 归档后仍要求读取可变 WORKING.json 才能验证历史架构。

不新增仓库外 discussion 共享 tmp。1.0.0 已有独立 Review Package 的隔离和证据保留规则继续适用，不借此任务随意改变。

# 9. 严格约束候选生成与正式冻结

不仅修改 Skill 文案，还要在确定性执行路径上实施校验。

候选必须绑定来源 discussion ID、revision 和内容摘要。关键架构决定或章节应能追溯到对应有效状态节点。

正式架构不能纳入：

- 未确认的 Agent 建议；
- 因依赖变化而失效的旧结论；
- 明确排除的本轮能力；
- 没有适用性或需求依据的组件。

Agent 可以展开已确认方案的职责说明、文案和图表，不要求用户逐句批准；出现新的实质性架构选择时必须回到讨论状态机。

草稿允许明确标记未决项，但不能冒充正式冻结产物。

保留既有门禁：

- 明确正式生成或冻结意图；
- 用户选择具体项目架构版本；
- 独立上下文审查；
- 候选及原始资料绑定；
- concern 覆盖；
- MD/PDF/PlantUML/manifest 一致性；
- 历史版本或 revision 保护；
- CURRENT 最后发布；
- 失败不推进正式状态。

不得通过直接调用低层 freeze 动作、提交手写 candidate JSON 或 legacy 标志绕过新增门禁。

哈希与 schema 只能验证结构、版本和绑定，不能代替语义审查，也不能证明真实 Agent 独立性。

实现明确的失效规则：实质性决定变化使关联候选和审查失效；只读查询不触发状态变化。

# 12. 必须覆盖的验收

保留原有有效测试，并新增有实际断言的正向、负向、集成和回归测试。

至少覆盖：

A. 讨论与调度
- 乱序输入可记录，已答内容不重复询问；
- 同优先级与依赖调度稳定；
- 多技术分支可同时激活；
- CLI、SDK、库等不会被强行解释成服务器或 GUI；
- 无数据库、无中间件、无 Gateway 可正确表达；
- API 作为跨组件契约检查；
- GUI 占位不生成未经确认的后端功能；
- 预算、范围和硬约束冲突可被识别；
- 不适用分支不会生成多余组件。

B. 确认与修改
- Agent 建议不能自动确认；
- 默认值与继承结论有来源；
- 用户修改只使相关依赖失效；
- 拒绝候选不等于问题闭合；
- 冻结后修改开启新流程；
- 缺失必需决定、需复核项和冲突阻止正式冻结。

C. 状态安全
- 查询无写入副作用；
- 陈旧 revision 写入被拒绝；
- 并发更新不会丢失结果；
- 锁和中断恢复明确；
- 损坏状态不会静默清空；
- 未授权路径、路径穿越和危险符号链接被拒绝；
- 多 worktree 不产生相互竞争的权威状态；
- Greenfield 写入讨论文件后不会误分类。

D. 归档与绑定
- 归档完整且幂等；
- 失败保留可恢复状态；
- 历史快照不可被原地覆盖；
- WORKING.json 后续变化不破坏历史产物验证；
- 新决定使旧候选和审查失效；
- 状态推进与哈希绑定不形成循环；
- 独立审查与真实轨迹不会被当作草稿清理。

E. 兼容与发行
- 旧格式读取及显式迁移；
- 未经授权不写 Existing Repository；
- 原有 DevOps 行为保持；
- 安装器不隐式迁移或 bootstrap；
- npm/pnpm 项目级与全局安装；
- 当前安装和历史版本运行时隔离；
- 历史 1.0.0 产物不变；
- 真实 MD/PDF/PlantUML 验证；
- 本地和 GitHub CI 共用核心验证；
- Windows、macOS、Linux 实际 CI 矩阵。

复跑历史兼容测试时，使用对应历史发布包、隔离 fixture 或版本感知入口，不修改冻结的旧测试以适配新版。

F. 真实 Agent 行为
使用真实 fresh-context Agent 验证：

- 从文件续接讨论；
- 区分建议和用户确认；
- 修改上游后处理失效；
- 正确查询状态；
- 拒绝越权写入或绕过门禁；
- 正确使用候选、审查和冻结输入；
- canonical 写回后由另一新上下文继续。

模拟单元测试与真实 Agent 行为证据分别记录。缺少独立 Agent 能力时，对应门禁未完成，不能以人工构造 trace 冒充通过。

# 13. 独立审查、构建、CI 与发布

按仓库既有流程执行：

1. 完成最小实现及文档。
2. 运行本地验证、负向测试、回归和构建一致性检查。
3. 启动 fresh-context 独立审查。
4. 审查者直接读取原始需求、源代码、测试、变更和审查任务；主 Agent 的自评只作为 ADVISORY。
5. 修复阻塞问题，复测并重新审查受影响内容。
6. 从接受的源状态构建 release/1.1.0。
7. 验证真实 npm/pnpm 安装及版本绑定。
8. 通过既有 PR 和真实 GitHub CI。
9. 集成到 canonical 主目录，确认接受的提交已进入正式分支，完成主目录验证与进度更新。
10. 按已有发布流程和实际授权完成 GitHub Release、npm 发行及发布后验证。

所有远程操作仅针对本任务明确的仓库和 architecture-governance-skills 包，遵守现有平台授权、保护规则和审批要求。

需要 push、PR、merge、GitHub Release、npm publish 等权限时，申请实际缺少的具体授权。未取得发布授权不得发布，不把可发布状态报告为已发布。

不得强推主分支、删除保护规则、覆盖历史 tag，或借 owner/admin 能力绕过不能 bypass 的完整性和必需检查。

正式发布前确认：

- 接受的源提交；
- tag 对应提交；
- 构建产物；
- GitHub 发布包；
- npm 待发布包；

具有一致且可核验的来源与哈希。

正式发布后实际验证指定 1.1.0 的获取与安装。只有在 latest 已按授权更新且验证一致时，才宣称 latest=1.1.0。

不要用本地 dry-run、模拟安装或创建 Release 页面代替实际 registry 发布验证。

已发布字节不可为补写证据而修改；后续发布验证记录与已发布产物保持明确边界。
